### Bug #1 — The Root Cause: `conversation_id` Mismatch (Critical)

This is almost certainly why you have to refresh.

The Supabase Realtime subscription in `useChat.js` filters by:
```
filter: `conversation_id=eq.${convId}`

The `convId` comes from `GET /messages` → `conv["id"]` from Zernio's API.

**The problem**: If Zernio sends the conversation ID in a different field in the webhook vs. what the REST API returns, the IDs won't match. The frontend subscribes to `conv_id = "abc"` but the webhook inserts with `conv_id = "xyz"`. Supabase Realtime fires, but the filter doesn't match, so the frontend never receives the event.

### Bug #2 — Supabase Realtime Requires Row-Level Security (RLS) to be Configured (Critical)

Supabase Realtime with `postgres_changes` only broadcasts to clients if:
1. Realtime is enabled on the `messages` table (Dashboard → Database → Replication)
2. RLS is either **disabled** on the table OR there's a policy that allows the anon key to `SELECT` the rows

You're using the **anon key** on the frontend. If RLS is enabled on `messages` with no permissive SELECT policy for `anon`, Supabase Realtime will silently drop the events — the subscription appears to work (no error) but you never receive payloads. This is a very common silent failure.

In `useChat.js`:
```js

Those messages won't be received in real-time and won't show until refresh. This is a race condition, not a bug per se, but it explains intermittent misses.

```python

There's no signature verification or secret token check. Anyone who knows the URL can POST arbitrary data and insert fake messages into your database. Zernio likely provides a webhook secret — it should be validated via HMAC or a shared secret header.
